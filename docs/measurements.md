# feature/fast-switch — 実測記録

[fork-changes.md](fork-changes.md) に書いた数字の根拠。すべて実機のログの時刻から
出したもので、推定にはその旨を書いてある。

計測の前提は [fork-changes.md](fork-changes.md) の「確認のしかた」を参照。特に
**RTC に電池が無いので日付は毎回同じ値に戻る**こと、起動間の比較には
`boot total`（CLOCK_MONOTONIC）を使うことに注意。

---

## 1. 起動: 4819ms → 1440ms

映像が出るまでの時間。全設定 OFF（純正相当）からの積み上げ。

| 状態 | 映像まで |
|---|---|
| 全 OFF | 4819ms |
| Async Display のみ | 3830ms |
| + Async Tuner Init | 2845ms |
| + Early Video Timing | 1988ms |
| + Defer Menu Build + Dual-Chip EFUSE Read | **1440ms** |

**70% 減。** ただし下の「セットで効く」を読むこと。

### 1.1 内訳（Async Display ON、映像まで 3.83 秒の時点）

| 区間 | 時間 | 備考 |
|---|---|---|
| アプリ開始 → rtc_init | 139ms | settings 30ms、language_init 47ms、pclk cp/rm 26ms |
| device_init | 185ms | IT66021 / IT66121 / TP2825 / DM5680 |
| lvgl_init | 15ms | |
| main_menu_init | 589〜679ms | 裏スレッド 2 本と CPU を取り合う |
| OLED_Startup | 54ms | 温度テスト |
| Display_UI_init | 54ms | aww ×5 = 45ms |
| osd_init | 158ms | 1080p 用セットも常に構築 |
| **DM6302_init** | **1795ms** | クリティカルパス最大。usleep は 101ms だけで残りは I2C 転送 |
| dispw 720p60（裏） | 1077ms | DM6302_init に完全に隠れた |
| Display_720P60_50 | 88ms | **ここで映像が出る** |
| audio_sel.sh | 477ms | 映像後、メインループを止める |
| wlan_stop.sh | 1077ms | `sleep 1` が全て。映像後 1.1 秒 OSD と入力が止まる |

### 1.2 3 本のトラックが均衡している（重要）

最速の 1440ms の起動を、アプリ開始を 0 として分解する。

| トラック | 開始 | 終了 |
|---|---|---|
| dispw | 179ms | **1298ms** |
| 受信機初期化 | 106ms | **1300ms** |
| メインスレッド | 0 | **1313ms** |

映像 = 1313 + 127 = **1440ms**。**3 本が 15ms 以内に揃っている。**

つまり **1 本だけ短くしても、次に長いものが顔を出すだけ。** 一つ前の 1988ms の
段階で試算すると、メニュー構築 976ms を丸ごと消しても受信機（1785ms）が律速に
なり、映像は 1915ms — わずか 73ms しか縮まない。

**残っているのは dispw の 1117ms で、これが床。** 開始をさらに早める余地は
179 → 約 100ms 程度なので、映像は 1350ms 前後が限界。dispw は外部コマンドで
中身を短縮する手段がない。**起動側は実質的に打ち止め。**

### 1.3 設定は「セット」で効く

| 設定の組み合わせ | 映像まで |
|---|---|
| 前倒しなし・Defer OFF・逐次 EFUSE | 1791ms |
| **前倒しあり**・Defer OFF・逐次 EFUSE | **2097ms** ← 悪化 |
| 前倒しあり・Defer ON・同時 EFUSE | **1440ms** |

前倒しだけを入れると**遅くなる**。受信機ワーカーを 42ms に前倒ししたことで、
EFUSE の 637ms がメインスレッドの IT66021/IT66121 初期化と重なり、同じ作業が
185ms → 406ms に伸びた。

**シングルコアでは I2C を叩くスレッド同士は重ならない。** 並行に走らせても、
どちらかが待つだけで総和は減らない。

### 1.4 Async Tuner Init の実効果はほぼゼロ（訂正記録）

一度「583ms 短縮」と報告したが誤り。差の大半は当時の自作バグが OFF 側を遅くした
もの。それを除くと ON と OFF の差は **28ms**。

理由: OFF でも受信機初期化と dispw は元から 99% 重なっていた。**Async Display
だけで受信機は完全に隠れており、Async Tuner Init が隠す余地はもう無い。**

単独では async_display −1092ms、async_tuner −844ms。両方でも **−1120ms** で、
816ms 分が重複している。だから Async Tuner Init は Early Video Timing と組み合わせ
たときに初めて意味を持つ（dispw を起動時に前倒しすると、切り替えで受信機初期化を
隠してくれるものが無くなるため）。

### 1.5 Dual-Chip EFUSE Read の検証

2 チップ同時読みが校正データを正しく読めているかを、構造体全体のハッシュで確認した。

| | 逐次読み | 同時読み |
|---|---|---|
| チップ 1 | band_num=2 bandgap=00002080 ical=1 rcal=1 **ea4dc8cf** | 同左 **ea4dc8cf** |
| チップ 2 | band_num=2 bandgap=00002080 ical=4 rcal=0 **3c0f97a7** | 同左 **3c0f97a7** |

**ビット単位で同一。** 所要は 637ms（349 + 288）→ 422ms で **−215ms**。
band_num=2 とバンド数が少ないため、想定した −330ms には届かなかった。

## 2. メニューへの切り替え

`switch mark: to_menu start` から `menu shown` まで。

| 状況 | 修正前 | 修正後 |
|---|---|---|
| 録画していない | 7 / 17ms | 6 / 7ms |
| 録画 3 秒以上の後 | 128 / 143ms | 18 / 26 / 33ms |
| 録画 3 秒未満で戻した | **1467 / 2029 / 2030ms** | **18 / 19 / 186ms** |

**切り替え処理そのものは 10〜25ms。** Menu Over Video が ON なら `Display_UI()` の
1.1 秒は最初から走らない。残っていた差は全部 `dvr_cmd(DVR_STOP)` の待ちだった。

### 2.1 録画プロセスは開始から約 3 秒経つまで確定しない

停止待ちを、直前の録画がどれだけ続いたかと並べた実測。

| 録画継続 | 停止待ち | 合計 |
|---|---|---|
| 6.09s | 101ms | 6.19s |
| 4.26s | 121ms | 4.38s |
| 3.35s | 121ms | 3.47s |
| 1.49s | 1451ms | **2.94s** |
| 0.74s | 2012ms | 2.75s（上限） |
| 0.25s | 2011ms | 2.26s（上限） |

合計がおよそ 2.9〜3.0 秒で頭打ちになる。3 秒より早く止めると残りを待たされ、
2000ms の上限（元の `sleep(2)` と同じ）に当たる。

Defer DVR Stop で待ちを次の録画開始へ移した結果、そこでの実測は
**0 / 0 / 0 / 0 / 303 / 483 / 727ms** — 最大でも 727ms で、しかもボタン操作の裏
（周辺スレッド）で消化される。

### 2.2 Poll DVR Start

`record start took`: 484（初回）/ 81 / 142 / 123 / 101 / 148 / 101 / 122ms。
すべて 2000ms の固定待ちより大幅に短い。

## 3. 起動時の I2C バス衝突

`Async Tuner Init` が ON のとき、チューナ初期化とメインスレッドの OLED 初期化が
同じ I2C バスで衝突することがある。頻度はおよそ 6 回に 1 回。

| | 通常 | 衝突時 |
|---|---|---|
| M0 イメージ転送 | 92ms | **10147ms** |
| OLED 初期化 | 94ms | **9955ms** |
| boot total | 2400ms | **12957ms** |

`DM6302_init()` は実行中ずっとバスを 1MHz に上げるが、OLED を読み書きする FPGA は
1MHz で応答できない。本来 30µs の 1 転送が約 39ms かかっていた（クロックストレッチ
かリトライで、待ち行列ではない）。

`i2c.c` のターンストルは両者を公平に分け合わせるが、それは飢餓を防ぐためのもので、
応答しない速度の通信を速くはできない。**律儀に交互に譲った結果、両方が等しく
100 倍遅くなった。**

### 3.1 対策後の実測

`OLED_Startup()` の前でワーカーの完了を待つようにした後の 2 回の起動。

| | 待ち | OLED | M0 | boot total |
|---|---|---|---|---|
| 衝突するはずだった起動 | **316ms** | 53ms | 92ms | **2549ms** |
| 通常の起動 | 6ms | 53ms | 93ms | 2345ms |

衝突する側のログ:

```
04:01:56.043  M0 done                                    ← チューナの転送完了
04:01:56.043  System Execute: aww 0x05002814 0x00000058  ← バスを 200kHz に戻す
04:01:56.056  HDZero: async open collected
04:01:56.056  boot step: wait for the tuner bus 316ms     ← ここまで待った
04:01:56.085  OLED temp test: ...                        ← 200kHz で全速
```

**払った代償 316ms、避けた損失 約 10 秒。**

`create_select_item()` が全ページで `MAX_PANELS`（32）個の隠しパネルを作っていたのを、
各ページが必要な行数だけにした。

## 5. 実機で失敗した試み

### 5.1 720p Playback

Playback を 720p のまま表示して `dispw` の 1.1 秒 × 2 を消す試み。**実機で表示が
壊れたため撤去した。**

症状: ラインごとの横ずれ、縦は上 1/4 程度、紫が強い、まばらなランダムピクセル。
**長押ししてもメニューに戻れなかった。**

特定できたバグ: `lv_disp_get_hor_res()` は**パネルの解像度ではない**。
`DRAW_HOR_RES_HD = 1280 + DISP_OVERSCAN(8) = 1288`。LVGL の描画バッファはオーバー
スキャン込みの値を返す。同じ誤りは 1080p でも起きており（1928×1088）、トグル OFF
でも映像の表示矩形が 8px ずれていた。

ただし紫やランダムピクセル、縦 1/4 は矩形のずれだけでは説明がつかない。FPGA の
他の設定（0x84 / 0xa7 / 0x8C、クロック位相）が 720p60 のタイミングで UI 用の値の
まま妥当かどうかは、ソースからは判断できなかった。**その判断が誤っていた。**

**再挑戦するなら:** まず 1080p のまま `vdec2vo.c` の `stDispRect` を 1920×1080 に
直す小さく確実な修正から。それが正しく映ることを確認してから 720p を試す。

### 5.2 その他の訂正記録

- Async Tuner Init の「583ms 短縮」は誤り（1.4 参照）。実効は 28ms
- Playback の一覧画面が縮小される件について、最初「録画が 720p で表示面が 1080p
  だから拡大されていない」と答えたが的外れ。実際はメニューの縮小率が再計算されて
  いなかっただけ。**症状の主語を確かめずに機構を説明した失敗**

## 5. チューナ初期化のバス速度: 1.2MHz vs 800kHz（2026-09-12）

`Switch Speed → Tuner Bus` を切り替え、Wide/Narrow ボタンで `DM6302_init()` を連続実行。
1 回の初期化 = `twi: tuner bus …` から `DM6302 after init` まで。`Short I2C Timeout` ON、
`Burst Tuner Writes` ON、`Dual-Chip EFUSE Read` ON。ログ [docs/logs/tuner-bus-800k-vs-1200k.log.gz](logs/tuner-bus-800k-vs-1200k.log.gz)。

| バス速度 | 初期化回数 | 詰まりのあった回 | 詰まり合計 | 正常時の初期化時間 (中央値 / 最小 / 最大) |
|---|---|---|---|---|
| **1.2MHz**（純正 `0x08`） | 41 | **4 回（5 件）** | 2524ms | 768 / 758 / 807ms |
| **800kHz**（`0x10`） | 20 | **0 回** | 0 | 886 / 855 / 902ms |

- 詰まり 1 件 = FPGA への burst 転送 1 回が **501〜510ms**（ドライバのタイムアウト 500ms に
  張り付く。`Short I2C Timeout` が無ければ 5006ms だった値）
- 800kHz の代償は **+118ms/回（+15%）**。転送速度の比 1.5 倍より小さいのは、
  初期化の時間がバス転送だけでは決まらないため（`usleep` 101ms、FPGA 側の待ち）
- **平均で比べると**: 1.2MHz は 41 回中 4 回の詰まりを含めて 830ms/回。タイムアウトが
  純正の 5 秒のままなら 5 件 × 5000ms が乗って **約 1380ms/回**。800kHz は常に 886ms
- **カーネルの TWI2 CCR 既定値は `0x58`（200kHz）、ビット 7（duty）は無い**（起動時に
  書いて読み戻して確認）。純正が復帰に書く `0x58` はカーネル既定と同じで、duty の
  副作用は無かった。40% duty の道は V5 には存在しない

**結論:** 800kHz は 20 回中 0 回の詰まりで、初期化 1 回あたりの平均時間は純正 1.2MHz
（タイムアウト 5 秒）より約 500ms 短い。規格内に収めて速くもなる。
